- Navigation items and the current dealership scope come from src/components/layout/navConfig.ts (useActiveScope); sidebar, phone menu, banner and pages must use it so they never disagree.
- New signup authorization is enforced by handle_new_user against invitations, and all AI functions use _shared/requireDealership after authentication; frontend AI errors use aiErrors so server denials are not hidden by retries or fallback scores. Why: OAuth bypasses browser checks and AI access must remain server-enforced.
- Scores and completions are service-role-only: evaluate-session saves authenticated users' evaluations; complete-module grades submitted answers; record-drill-score verifies canonical answer choices and uses a locked, idempotent run receipt to record first/best scores. Keep _shared/staticScoreKeys synchronized with static question banks. Why: browser-provided totals and local completion caches are not trusted evidence.
- Course assignments live in course_assignments (per person) + course_team_assignments (whole team, auto-applied to new profiles by trigger); all writes and assignment emails go through the assign-course function, reminders/new-hire emails through the daily send-scheduled-emails run; every app email sends via _shared/sendAppEmail.ts (managed send helper + email_send_log row). Why: one server-checked path keeps managers inside their dealership and avoids duplicate emails.
- Game assignments mirror the course ones (game_assignments + game_team_assignments, same trigger, same assign-course path) but are keyed by each game's drill_scores drill_key — mapped in src/lib/drills.ts drillScoreKey and mirrored in _shared/gameAssignmentEmail.ts DRILL_META. A game counts as done once a drill_scores row exists for that key. Why: games live in code, not the database, so the key map must stay in sync on both sides.
- Training-video storage is private and read policies enforce dealership folder ownership or Super Admin access; persist stable references and sign at playback without changing progress keys. Why: stored signed URLs expire and public URLs bypass access controls.
- All AI functions preserve upstream failure statuses through _shared/aiGatewayErrors; transcription uses the gateway with the existing multipart audio/{text} contract. Why: credit exhaustion and denials must not become generic errors or fallback voice output.
- All five AI functions call _shared/aiRateLimit after verified membership; service-role consume_ai_request serializes shared per-user rolling windows and checks Super Admin exemption in the database. Why: concurrent requests and function switching must not bypass limits.
- Passing module_completions issue immutable course_certificates through a database trigger in the same transaction; Certificates reads issued records and canonical custom-course keys. Why: certificates must rely on trusted passing scores and include custom courses marked alwaysAccessible for navigation.
- App routes nest under AuthGuard, with Team/Admin under RoleGuard using verified role flags; the database roles are manager and super_admin, not an invented admin role. Why: protected pages must not mount for signed-out or unauthorized users.
- Certification percentages use useCertificationProgress and calculateTrainingProgress: scoped certifiable catalog, canonical module keys and distinct passing issued certificates; team completion/category views use the same catalog and slot math with trusted completions. Why: session scores and partial catalogs are not certification evidence.
- Team and Admin load fetchDealershipMetrics: current dealership profiles with assigned app roles and completed sessions matching both current user membership and session dealership. Why: unassigned accounts, started sessions and old dealership history must not inflate counts; recent activity is a separate metric.
- Session names use resolveSessionTitle/useSessionTitles across lists, details and exports. Why: custom scenario identifiers must resolve through authorized scenario records rather than display UUIDs.
- evaluate-session requests a strict JSON schema and validates the entire response; invalid/incomplete output returns an explicit failure without saving scores, and training Retry reuses the same session. Why: regex extraction and synthetic scores conceal failed evaluations.
- Password recovery initializes PKCE, recovery hashes or existing validated sessions before rendering; new password rules are shared by signup and reset. Why: link formats and validation must not diverge.
